# AirMic 技术方案

> 版本 v0.1 · 2026-10-24
> 本文是**实现的真相源**：架构、协议、数据模型、模块划分、里程碑与风险。
> 产品逻辑看 `prototype/需求说明书.md`，视觉契约看 `prototype/DESIGN.md`。

---

## 1. 目标形态

| 端 | 形态 | 技术栈 | 交付物 |
|---|---|---|---|
| 电脑端 | macOS 菜单栏应用（不占 Dock） | **纯 Swift / SwiftUI**（SwiftPM，无 Rust、无 WebView） | `AirMic.app` |
| 手机端 | Android App | **Capacitor + React**（复用原型 UI）+ Kotlin 原生插件 | `AirMic.apk` |

**为什么电脑端不用 Tauri**：原型文档定的路线是「Tauri 2 包装」，但实际评估后选择纯 Swift，
原因是三条：

1. **虚拟音频必须 native** —— 反正要写 Swift（CoreAudio），UI 就一起写，少一层进程与 IPC。
2. **内存**：纯 Swift 菜单栏 App 常驻约 15–20MB；Tauri 带 WKWebView 大约 30–60MB。
   原型的性能指标是「常驻内存 < 40MB」，纯 Swift 才稳。
3. **观感**：菜单栏面板要「完全跟随 macOS」（毛玻璃、系统色、原生控件），
   SwiftUI 天然做到；WebView 画出来的面板总归差一口气。

**为什么手机端用 Capacitor 而不是原生 Compose**：原型那 2500 行 React UI
（麦克风页 / 预案编辑抽屉 / 磁铁库 / 磁贴 / 弹层）质量很高且已验证，
重写成 Compose 纯属浪费。Capacitor 让 React UI 跑在 WebView 里，
再用一个 Kotlin 插件做真活（mDNS 扫描、TCP 控制通道、AudioRecord→MediaCodec 推流）。
WebView 只负责界面，音频和网络全在原生层，延迟与稳定性不受影响。

## 3. 关键设计决策

### 3.1 编码：AAC-LC 而不是 Opus

- macOS 的 `AudioConverter` **不支持 Opus 解码**（实测 `AudioFormatGetProperty('opus')` = -50）。
- 用 Opus 就必须把 libopus 源码 vendor 进 App（外部依赖 + 体积 + 许可处理）。
- AAC-LC 两端都原生支持：安卓 `MediaCodec`（`audio/mp4a-latm`）、macOS `AudioConverter`。
- 代价：AAC-LC 一帧 1024 采样（48kHz 下 21.3ms）+ 编码器 priming，整体延迟比 Opus 高约 30–50ms。
  对「按住说话把声音送进电脑麦克风」这个场景完全够用。
- 协议里预留了 codec 字段，后续要换 Opus 只需两端各改一处 + vendor libopus。

### 3.2 虚拟麦克风：先依赖 BlackHole

- 用户装一次 BlackHole（开源、免费），AirMic 内置一步引导。
- AirMic 把解码后的 PCM 写进 BlackHole 的输出流 → 系统「声音 → 输入」里选 BlackHole，
  任意录音 App 录到的就是手机麦克风。
- 自研 AudioDriverKit 驱动（AirMic Input）留到 v2：需要向 Apple 申请
  `com.apple.developer.driverkit` entitlement 并签名分发，周期不可控。

### 3.3 写虚拟设备用 CoreAudio IOProc，不用 AUHAL

macOS 14 SDK 已经移除了经典 AudioUnit API（`AudioUnitStart` / `kAudioUnitProperty_EnableIO`），
所以直接用 `AudioDeviceCreateIOProcID` + `AudioDeviceStart`：
在 IO 回调里把 PCM 填进设备的输出缓冲。少一层 AUHAL 协商，也更贴近真实设备行为。

### 3.4 配置以电脑端为准，编辑入口在手机端

磁贴按下要在电脑上执行，所以电脑必须知道键位。
- 手机端连上 → 推一次全量配置（磁铁 + 预案）→ 电脑端存盘。
- 之后每次改动推一次全量（字段少，不值得做 diff）。
- 删磁铁时，电脑端会清掉所有预案里对它的引用（避免磁贴指向不存在的磁铁）。

### 3.4.1 菜单栏窗口用 NSPanel，不用 MenuBarExtra

SwiftUI 的 `MenuBarExtra` 有两个解决不了的问题：

1. 窗口是不透明的，`Material` 只能画出接近实心的底色 —— 做不出控制中心那种
   真正透出桌面的毛玻璃。
2. 它自己会改窗口高度，SwiftUI 又在同时做内容布局动画，两边节奏对不上，
   展开/收起时内容会叠在一起。

所以菜单栏部分改成 AppKit：`NSStatusItem` + 无边框 `NSPanel` +
`NSVisualEffectView(.popover, behindWindow)`。窗口高度**只由我们控制**
（顶部固定、向下生长），内容不参与布局动画，从根上消除叠影。

### 3.5 服务端是全局单例

菜单栏应用的 SwiftUI 场景里，`@StateObject` 持有的对象**会在场景安装之前就被释放**，
结果是：端口在监听，但连进来的连接没人应答（本人踩过，症状非常隐蔽）。

所以服务端是 `AirMicServer.shared`（全局单例，`@Published` 直接给界面用），
界面层只是一个转发器。**凡是要活到 App 结束的东西，都不能挂在视图生命周期上。**

### 3.6 配对信息用文件存，不用钥匙串

钥匙串里的条目属于「创建它的那个程序」。未签名 / ad-hoc 签名的构建之间互相读
会触发系统授权弹窗，并且**阻塞**读取 —— 开发期同样表现为「连上了但不回话」。

现在存在 `~/Library/Application Support/AirMic/pairing.json`（权限 0600）。
等有了稳定的开发者签名，再换回钥匙串（代码里留了位置）。

### 3.7 签名身份必须稳定

`package-mac.sh` 默认用 `.toolchain/signing/` 里的自签名证书（`AirMic Dev`）签名。
**不要改回 ad-hoc**：ad-hoc 签名的身份是二进制哈希，每次重新编译都会变，
macOS 的「辅助功能」授权就跟着失效 —— 用户会看到开关是开的、程序却说没权限。

换了签名身份之后，需要在系统设置里**把旧的 AirMic 删掉、重新添加一次**；
之后重打包不用再授权。

### 3.8 路由不可变

未配对 → 永远进设备页；已配对 → 直接进麦克风页。手机端 store 的 `paired` 由
`welcome.pairingRequired` 决定。

## 4. 数据模型

### 磁铁（全局，可复用）

```ts
type HotkeyMagnet = {
  id: string
  label: string        // 「语音输入」
  icon: string         // lucide 图标名
  modifiers: string[]  // cmd / shift / ctrl / alt
  key: string | null   // 键盘主键
  mouse: string | null // 鼠标键（与键盘主键互斥）
  text?: string | null // 文本磁片的内容（非空即文本磁片，此时 key/mouse 为 null）
}
```

显示串（`⌘⇧V`）与下发串（`["cmd","shift","v"]`）**都是算出来的**，不存字段 ——
和原型 `src/lib/hotkey.ts` 完全一致，电脑端 Swift 侧有同样的实现。

#### 文本磁片

`text` 非空的磁片不是快捷键，而是**一段提前编辑好的文字**。
触发时手机端发 `text.paste`，电脑端（`TextPaster.swift`）：

1. 快照当前剪贴板（所有 item 的所有 UTI 数据）；
2. 写入这段文字；
3. 激活目标应用，发 ⌘V；
4. 1.2 秒后，若剪贴板里仍是这段文字，还原用户原来的剪贴板
   （用户中途自己复制了别的，就不动）。连续多段文本只保留第一段之前的快照。

> **为什么不用 `CGEvent.keyboardSetUnicodeString` 直接注入**：它只对标准 AppKit
> 输入框有效，Flutter / Electron / 远程桌面 / 游戏会直接丢掉这些 Unicode 字符，
> 症状是「什么都没发生」但日志一切正常。⌘V 是所有应用都认的路径。
> 代价是短暂占用剪贴板，所以要做快照和还原。

没有键可以「按住」，所以文本磁片在长按位置就是**按下时粘贴一次**。
磁片组绑到长按时，组里**第一个有组合键的步骤**才是按住的那一个：
排在它前面的文本在按下时粘贴，排在后面的跟着其它步骤在松手后依次执行。

### 预案

```ts
type Preset = {
  id: string
  name: string
  appName: string | null   // 绑定的电脑前台应用；null = 默认预案
  appIds: string[]            // 绑定的应用 id（可多个，一个应用只属于一个预案）
  micPressId: string | null   // 点按「打开」时执行的磁铁
  micReleaseId: string | null // 点按「关闭」时执行的磁铁
  micHoldId: string | null    // 长按说话时按住 / 松开的磁铁（与上面独立）
  micHoldGroupId?: string | null // 长按绑磁片组（和 micHoldId 二选一）
  tiles: { id: string; magnetId?: string; groupId?: string }[] // 独立快捷键磁贴
  isDefault?: boolean
}
```

⚠️ `micPressId` / `micReleaseId` 与 `tiles` 是**两件事**，UI 上必须区分
（原型硬约束 10）。手机端与电脑端的数据结构完全一致。

长按可以绑**磁片组**：组里第一步跟着手指按住，松手后释放，剩下的步骤按
`intervalSeconds` 依次执行。点按（开 / 关）仍然只能绑单个磁片。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 用户没装 BlackHole | 「电脑麦克风」用不了 | 面板里明确引导（一键复制安装命令 + 打开官网）；检测到设备列表里没有虚拟设备时提示 |
| 首次运行要授辅助功能权限 | 快捷键静默失效 | 首次使用快捷键时检测 `AXIsProcessTrusted()`，弹窗说明去哪儿开 |
| 安卓后台杀进程 | 收音中断 | 前台服务 + `FOREGROUND_SERVICE_MICROPHONE` + WakeLock |
| 安卓 mDNS 收不到包 | 扫不到电脑 | `MulticastLock` 必须持有；Android 13+ 要 `NEARBY_WIFI_DEVICES` |
| 两端时钟不同步 | 延迟算不准 | 延迟一栏在拿到真实数据前显示 `[--]`，不编数字 |
| AAC 编码器 priming | 开头几十毫秒没声音 | 正常现象；解码端前几帧解不出数据，静默丢弃 |

## 8. 踩坑记录（都是实测踩出来的，别再踩一遍）

| 坑 | 症状 | 结论 |
|---|---|---|
| `@StateObject` 挂服务端 | 端口在监听，但连接进来**没人应答**；日志里能看到 `newConnectionHandler 触发` 但 `accept` 不执行 | 服务端改全局单例 `AirMicServer.shared`（§3.5） |
| 钥匙串跨程序读取 | 未签名 / ad-hoc 签名的两个构建互相读钥匙串条目 → 系统弹授权框并**阻塞**读取 → 表现同上 | 配对信息改存文件（§3.6） |
| `AudioConverterFillComplexBuffer` 的输出包大小 | 解码永远只出 1 个采样，后面全是 0 | 这个参数是**帧数**不是字节数：给 1024（= 一帧采样数）才正常；给大了转换器会想要更多输入，队列一空就进 EOF 状态，之后再也不产出 |
| UDP 用 `NWConnection` 当服务端 | 端口没监听，发包报 connection refused | UDP 服务端必须用 `NWListener` |
| `receiveMessage` 的 `isComplete` | 只有第一个数据报能收到，后面全丢 | UDP 收完一个数据报就会报 `isComplete`，不能拿它当结束条件，要继续订阅 |
| 经典 AudioUnit API | `AudioUnitStart` / `kAudioUnitProperty_EnableIO` 在 macOS 14 SDK 里**已被移除** | 改用 CoreAudio 的 `AudioDeviceCreateIOProcID` + `AudioDeviceStart`（§3.3） |
| 统计不更新 | 面板上丢包/延迟永远是 `[--]` | 音频管线的统计要每秒回写到服务端的 `@Published` 属性 |
| macOS 不支持 Opus | `AudioFormatGetProperty('opus')` = -50 | 改用 AAC-LC（§3.1） |
| `AudioDeviceIOProc` 参数顺序 | 音频包都在进、解码也正常，但电脑完全听不到；`写设备 0 帧` | 回调签名是 `(device, now, inInputData, inInputTime, outOutputData, inOutputTime, clientData)`。**第 3 个是输入、第 5 个才是输出** —— 往输入缓冲里填等于什么都没写出去 |
| CGEvent 键码不是 ASCII | ⌘Space 能用，⌘T / ⌘V / ⌘C 全没反应 | 字母的虚拟键码是 ANSI 布局表（`kVK_ANSI_V` = 9），不是 `'V'.ascii = 86`。空格/回车有独立键码所以碰巧能用，字母数字必须查表 |
| ad-hoc 签名导致授权失效 | 「辅助功能」开关明明开着，`AXIsProcessTrusted()` 却是 false；每次重新打包都要重新授权 | ad-hoc 的签名身份是 cdhash，重编译就变，TCC 按签名绑定授权。改用项目内自签名证书（`scripts/setup-signing.sh`），指定要求是 `identifier + certificate leaf`，跨重打包稳定 |
| Swift `Tile.magnetId` 必填 | 手机端只要有**磁片组**磁贴（只有 `groupId`），整条 `config.push` 就解码失败，电脑端日志里是 `消息解析失败：The data couldn't be read because it is missing`，配置从此不再更新 | `magnetId` 改成可选；`sanitize` 遇到 `groupId` 的磁贴原样保留（电脑端不知道有哪些组） |

**已验证的链路**（不需要安卓真机）：

```bash
cd mac && swift build
.build/debug/airmicd serve --audio        # 开控制通道 + 音频管线
.build/debug/airmicd tone 127.0.0.1 47472 5   # 合成 440Hz → AAC → UDP
# 服务端日志：已解码 50/100/150/200 帧，丢包 0.0%，欠载 0
```

`airmicd aactest` 是不经过网络的编解码自测（PCM → AAC → PCM，1:1 无损耗）。

## 9. 诊断日志（排查「没声音」用这个）

日志文件：`~/Library/Logs/AirMic/airmic.log`
面板 →「详细设置」→「复制诊断日志」可以直接把现场数据复制到剪贴板。

收音时每秒一行：

```
[AUDIO] recv=94 lost=0 decoded=2.0s empty=0 rendered=0.4s peak=0.31 queued=33152 underrun=0
```

按这三段就能定位卡在哪儿：

| 现象 | 说明 | 去哪查 |
|---|---|---|
| `recv=0` | **音频包根本没到电脑** | 手机有没有在收音、Wi-Fi 是否同一网段、UDP 47472 有没有被防火墙拦 |
| `recv>0` 但 `decoded=0` | 包到了但解不出来 | 编码格式（AAC-LC）是否一致、AU 是否被截断 |
| `decoded>0` 但 `rendered=0` | 解出来了但**没写进设备** | 输出设备选择、IOProc 是否启动、设备是否支持该格式 |
| `rendered>0` 但听不到 | 写进去了 | 监听的是不是同一个设备（BlackHole 不会自己出声） |

`peak` 是写出去的最大振幅，正常说话应当在 0.05–0.4 之间。
